## 2. Исправленные баги (root cause → фикс)

### BUG-1. Парсинг опыта не работал ни на одном реальном резюме
- **Root cause 1**: `db/builders.py` — регэксп `опыт\s+работы:\s*(\d+)\s*(?:лет|год|года)`
  требует литеральный префикс с двоеточием. Реальные данные: `«2 года и 1 месяц»`
  (значение поля без префикса), `«Стаж 10 лет»`, `«полгода»`, периоды
  `«апрель 2021 — настоящее время»`. Совпадений — ноль, `experience_years = None`
  у всех, тай-брейк по опыту не работал никогда.
- **Root cause 2**: `api/routes.py::import_superjob_resumes` —
  `item.get("experience") or "Без опыта"` игнорировал `previously_held_positions`
  (95/100 резюме имеют позиции с периодами).
- **Root cause 3**: `api/nlp_parser.py` вообще не содержал парсинга опыта и был
  мёртвым кодом: его никто не импортировал, а `SentenceTransformer` грузился
  на импорте модуля (сотни МБ) и не использовался; из-за транзитивного
  `api/__init__ → routes → data.synthetic → faker` модуль ещё и не импортировался.
- **Фикс**: робастный парсер `extract_experience_years()` в `api/nlp_parser.py`
  (явные формулировки → дробные «полгода/полтора» → сумма периодов с
  объединением пересечений → «без опыта» = 0.0; учебные строки отфильтрованы).
  `db.builders.experience_years`/`parse_raw_text_to_resume` и SuperJob-импорт
  используют его; `api/__init__.py` облегчен (FastAPI-приложение поднимается
  через `uvicorn api.main:app`, как и раньше); эмбеддер — ленивый.

### BUG-2. Очень низкие метрики скорера
- **Root cause 1 — гранулярность навыков**: требование `SQL` не закрывалось
  `MySQL/PostgreSQL/SQLite`, `Machine Learning` — `scikit-learn/PyTorch`,
  `Аналитика данных` — `Tableau/Power BI`. Полные семьи: новый модуль
  `scorer/skill_families.py` (SQL, ML/DL, анализ данных/BI, Big Data, ETL,
  JS, Java, тестирование, ООП, Linux, 1С, API, документация, английский).
- **Root cause 2 — фейковая «косинусная» мера**: `similarity.pair_cosine`
  считал BM25/10 — без естественной границы [0,1], с вырожденным IDF на
  корпусе из одного документа. Заменён на настоящий TF-IDF-косинус
  (сублинейный TF, IDF по корпусу в batch-режиме), имена функций сохранены.
- **Root cause 3 — производительность**: `category_of` компилировал regex на
  каждом вызове (395 000 вызовов `re._compile` на вакансию = 80 с) и
  `normalize_skill_set` прогонял ~1800 паттернов на навык на каждую пару.
  Фикс: предкомпиляция паттернов категорий + `lru_cache` (`category_of`,
  `_normalized_skill`). Итог: 61 с → 0.1 с на вакансию.
- **Root cause 4 — недетерминизм**: в таксономии 103 пары дубликатов по
  регистру (`PostgreSQL`/`postgresql`...), выбор написания зависел от
  хэш-сида процесса → matched/metrics «плясали» между запусками.
  Фикс: детерминированная дедупликация (`collapse_case`/`case_score`).
- **Root cause 5 — чёрный список против ground truth**: 16 ярлыков разметки
  (`ООП`, `API`, `Excel`...) были в BLACKLIST экстрактора — гарантированные FN.
  Эмпирика по 201 документу: защищать стоит только `ООП` (+12 TP/−1 FP),
  `КОМПАС`, `Стратегия`; «тестирование» (5/24), «api» (18/37), «разработка»
  (1/113) оставлены в чёрном списке. Итог — `PROTECTED_SKILLS` с обоснованием.

## 3. Прочие замечания ревью (не чинил — на решение владельцам)

1. **`scripts/skill_extractor.py` — устаревшая копия** `scorer/skill_extractor.py`
   (дрейфут уже сейчас: другой BLACKLIST). Тест `test_skill_extractor.py`
   импортировал именно её (починено на живой модуль). Рекомендую удалить файл.
2. **Duplicated knowledge (DRY)**: BLACKLIST/INLINE_ALIASES/`build_skill_pattern`
   скопированы в 5 файлах (`scripts/benchmark.py`, `benchmark_resumes.py`,
   `audit_resumes.py`, `error_analysis.py`, `scorer/skill_extractor.py`) и
   разошлись. Единый источник — `scorer/skill_extractor.py`.
3. **Битые пути в scripts/**: `benchmark*.py`, `error_analysis.py`,
   `audit_resumes.py` ждут `scripts/exel/{Вакансии,Резюме} в pdf/`, которых нет —
   PDF лежат в `AI-система для скоринга/`. Как следствие эти скрипты падают.
   Замена — новый `scripts/benchmark_real_data.py` (работает с `data/`).
4. **Ground truth размножен в 3 местах** (`data/`, `scripts/exel/`,
   `AI-система для скоринга/`) без синхронизации; в CSV-колонках есть шумовые
   ярлыки («разработка», «позиции», «сборка»).
5. **`metrics_by_category` в `rank_candidates`** сравнивает навыки резюме с
   навыками вакансии как с «истиной» — это мера покрытия требований, а не
   качества извлечения; в UI это может читаться как «плохие метрики» для
   валидных кандидатов с широким стеком (каждый лишний навык — «FP»).
6. **`/upload_vacancy` парсит вакансию резюме-парсером** (`parse_raw_text_to_resume`,
   ищет «Должность:») — работает случайно; для вакансий нужен свой шаблон.
7. **Требования к опыту вакансий** (`experience: "от 1 года"`) не участвуют в
   скоринге — только тай-брейк. Если бизнес хочет штрафовать за недобор опыта,
   нужно решение о весе (сейчас Skill-скор остаётся абсолютной мерой — это
   осознанный дизайн, задокументированный в `scorer/service.py`).
8. **P@5 в бенчмарке ≈ 0** — артефакт определения: порог rel≥0.5 при том, что
   максимальный ground-truth overlap во всём датасете 0.57. Порог стоит
   калибровать по перцентилю, а не по абсолюту.
9. `data/synthetic.py` остаётся в прод-роутах (`/generate_test_data`) — для
   демо ок, но смешивать синтетику с реальными SuperJob-резюме в одной Mongo
   не стоит (флаг `_synthetic` есть — используйте его в выборке пула).
